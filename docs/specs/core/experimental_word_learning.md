# 言葉の経験学習・比較実験版

状態: 一部実装（既存島の描画・BGMへ新方式の生活・会話・記録を接続。初回比較版全体は未完成）

更新日: 2026-09-25

## 対象範囲

LLMを搭載しない疑似AIの新しい言葉学習方式について、壁打ちで合意した方針、候補、未決定事項を管理する。既存方式を置換する実装指示ではない。

壁打ちは一つの論点の掘り下げが終わったら合意と再開点を記録し、次のチャットへ移る。実装を急ぐために必要な未決定事項を残して議論を打ち切らない。実装開始は別途ユーザーの依頼を待つ。

## 現在の実装仕様

### 手伝いの経験学習・会話と操作方針

- 通常画面では行き先を直接指定するボタン・人物選択・マップクリック移動を使わない。プレイヤーは会話で働きかけ、本人が行動を判断する。移動指定は `?debug=1` の内部検証専用で、製品の操作を拡張する土台にはしない。下記の指さし記述は内部検証の挙動を指す。
- 空腹と体力を常時メーター・百分率で表示する。空腹は `hunger`（大きいほど空腹）、体力は `1-fatigue`（大きいほど余力）で、判断に使う新方式の実値を投影する。旧版の年齢・筋力・知能・Gold等は未接続で、架空の値を表示しない。
- 手伝い開始時、師匠が今行う作業を言葉と実演で示す。実際に完了した作業とその実演ラベルが両方ある場合に、`work` と `work:職ID` を `demonstrated_work` として獲得する。カタログの `experienceMeanings` は初期知識から分離し、未知設定でも実演経験から結び付けられる。六つの初歩の作業語に限定した習得であり、職業全般の理解や関係文法を一括付与しない。
- 根拠は完了経験ID・師匠ID・実演ID。未完了・見ただけ・ノート閲覧・質問・同じ完了イベントの再通知では強化しない。旧保存の完了記録へ遡及付与せず、次に実演付きで手伝った際に覚える。学習根拠をノートと専用保存へ保持し、保存検証では対応する完了経験を確認する。
- 「どんな仕事をしたの？」は最後に完了した手伝いを、覚えた作業語で答える。「何をしたの？」「さっき何してた？」は直前の行動を参照し、手伝いなら同様に答える。「またやりたい？」「その人の仕事学びたい？」は注目中の師匠、指定した既知の作業、または最後の手伝いを参照する。空腹・疲労が強ければそれを伝え、それ以外は実際の作業負担から更新した興味で再試行／別のことを答える。
- 回答は質問・過去の関係の既知を要求する。関係未知設定では、作業語を学んでも質問の関係まで理解済みにしない。しぐさ設定では短文を強制しない。七言語に手伝いの振り返り・再試行質問の入口と作業語の別名を持つが、自由文全般の理解は未完成。
- 自律的な訪問先は未訪問への好奇心、前回訪問からの時間、実際の興味で選ぶ。経験済みの仕事の加点は `(interest-.08)*120`、返答の再試行境界も `.08` の初期調整値。同じ興味から再試行／別のことの傾向を返答と選択に反映する。質問だけで移動・興味・学習根拠を更新しない。返答は行動予約ではなく、その時点の意向であり、食事・休息や新しい出会いと競合する。

### 基本職6種の出会いと初歩の手伝い

- 次の到達目標は新方式のSteam体験版。ユーザーは「一人の子との暮らし＋基本職6種の師匠との出会い・初歩的な仕事経験」を目標に実装を進めることを承認した。Steam公開操作は別段階。下記は最初の職業導線であり、公開用体験版全体の完成ではない。
- 六職の活動地点を開始時から島の陸地に置く。冒険家は森、農家は畑、漁師は水辺、料理人はレストラン、鍛冶師は山に近い作業場所、建築士は陸地の作業場所を初期配置とする。既存の人物立ち絵を使う。語彙数で人物を出現させず、到着して初めて会ったことを記録する。冒険家の滞在期限・島外移動などの設定は未実装。
- 本人の自律散策で師匠を訪問する。人物クリック・人物一覧からの移動指定は上記の内部検証専用。プレイヤー向けの人物名を本人が職業語を理解した根拠にはしない。初対面の師匠の台詞は本人の発話・観察描写と表示を分け、再訪で同じ初対面を繰り返さない。
- 近くで見学した後、空腹・疲労が強ければ離れ、取り組める状態なら本人から手伝いを始める。三語条件・入門三問・旧Rankは接続しない。初歩の手伝いにプレイヤーの弟子入り承認ボタンを置かない。見学8秒、手伝い14〜18秒、体調の判断境界・作業負担・興味更新は調整用初期値。
- 初歩の内容は、冒険家の荷物運び、農家の石拾い、漁師の網修理、料理人の皿洗い、鍛冶師のふいご、建築士の図面写し。職別の完了件数と成果IDを保持し、開始／完了時点・体の前後差・実行時の理由を本人の経験へ残す。素材・Gold・資格・高度な技能の報酬はこの段階では付与しない。本格的な探検・農作物栽培・釣り・料理制作・装備鍛造・建築そのものの新方式接続は残作業。
- 他の師匠の仕事も試せる。経験済みの仕事・学び始めた相手を消さず、職を一つに固定しない。次の自律訪問は初対面への好奇心、最後に訪れた時点、実際の作業負担を踏まえた再試行への興味で選ぶ暫定モデル。正式な皆伝・高度な職業進行・転向制度は未実装。
- 出会いは `state.encounters`、相手ごとの見学・開始・成果・興味は `world.careers.people`、作業中は `world.mode=work` と `world.careers.current` で持つ。作業の時間更新は既存の新方式 `tick` 一つだけ。食事同様、進行中の手伝いを指さしで黙って破棄しない。完了成果は一度だけ付与する。
- 出会いと完了した手伝いはノート・試遊レポートへ含め、睡眠整理でも原経験への参照を保持する。読んだだけで仕事の経験や学習を増やさない。作業語の習得は上記の実演付き経験に限定し、職業名・文の関係を習得済みにしない。
- 三地点の既存島セーブは地形・生活地点・知識を保持したまま六人の活動地点を追加し、未遭遇の状態から始める。作業途中の保存は残り時間と消費済み状態を保持し、再開で完了成果を重複付与しない。旧版の師匠・セーブは変更しない。

### 既存島での比較起動

- `npm run start:word` / `start:words` は専用Electronから `experimental_word_island.html` を開く。Web確認の `start:web:words` も同じ島を開く。`experimental_word_learning.html` の仮広場は内部検証用として残す。
- 地形・川・森・山・畑・レストラン・薬局・川向こうの洞窟等は既存 `generateNatureMap()` と同じ生成規則・配置内容。既存セーブの個別島を取り込むのではなく、独立した新規島を作って専用保存に保持する。既存 `data.js` の素材・フレームと `view_renderer.js` の島描画・カメラ追従・キャラクター描画を再利用する。
- マップ生成とBGMの共通本体は `island_shared.js`。通常版もこれを読み、従来の `system.js` / `main.js` から呼ぶ。比較版は `system.js`、`main.js`、旧 `ai_core.js`、日課・住人更新・クラウド処理を読み込まない。描画用のactorに旧AIのupdateを付けず、生活時間の所有者は `ExperimentalWordWorld.tick` 一つだけとする。
- 理解の土台・生活知識・発話形式の三軸／八設定、姿の三択、チャット（Enter送信・IME確定の区別）、会話／ノート切替、試遊レポート、一時停止を保持。チャットで働きかけ見守る基本操作を使い、新方式の理解・判断へ渡す。直接移動の補助操作は内部検証限定。全職業・屋内・施設操作の移植はこの段階に含めない。
- `experimental_word_island_navigation.js` は既存地形タイルの陸地接続から経路を作り、水面を横切らない。初期位置と同じ陸地にある森のそばを採食と木陰の場所にし、上記の六職の活動地点にも接続する。移動中は到着先を注目済みにせず、到着時に知覚へ接続。採取・食事・休息の完了経験と、実際の前後差、名付け、状況回答、ノート、レポートは共通の新方式処理を使う。未知生活語を移動や回復だけで既知にしない。
- 島上の資源量・補充・回復は下記の新方式の初期調整値を維持。既存の農業・経済更新を重ねて回さない。比較版では発話後の5秒停止を外し、反応・吹き出し時間と生活更新を分離する。入力中・一時停止・非表示・レポート書出中の停止、不在分を進めない方針は維持。
- BGMは共通audioManagerから従来の `bgm_robot.mp3` / `bgm_spirit.mp3` / `bgm_seed.mp3` を選んだ姿に応じて再生する。音量変更は比較版の保存へ保持。音源配信はHTTP Rangeに対応する。既存のBGMを別の曲へ置き換えない。
- 専用 `word-life.json` と前回バックアップ、IPC呼出元照合、異常時停止を維持。`world.island` に配置・地点・音量、`world.route` に進行中の経路を含める。読込時に地形・地点・経路形式を検証する。旧仮広場の保存では知識・記録・設定・食事中の消費済み状態を保持し、位置だけ初回に島へ接続。以降は同じ島・同じ生活状態で再開する。旧ゲーム保存・旧画像調整localStorageは読み書きしない。
- 初期設問の詳細、新しい未知語／関係の習得、全施設への行動接続は残作業。島への接続を初回比較版全体の完成とは扱わない。

- ユーザーの2026-09-25の実装開始依頼により、`experimental_word_learning_core.js` と専用起動ページで初回の会話縦断試作を実装。既存方式の学習とタスクは [AI・言葉・タスク](ai_words_and_tasks.md) が所有し、変更していない。
- 既存の体験版／製品版分離は [Steam体験版・製品版の分離](../internal/steam_demo_and_full_release.md) が所有する。新旧の学習方式の分離とは別の軸である。

### 会話縦断試作の現在範囲

- 2026-09-25の追加実装で食事・欲求・回復経験・睡眠時の記録参照整理とElectron専用保存を接続した。詳細は下記「食事・回復経験と専用保存」を正本とする。過去の設計検討節の「資源補充／保存方針未決定」は今回の採用範囲では解消した。読めるノートは下記の限定範囲で実装。未知生活語・関係の習得は引き続き未実装。

- 専用Electronは専用AppData、単一起動、OS割当のローカルポートを使い、ウィンドウ終了時に内部サーバーも止める。`start:web:words` は4175番のWeb確認用で、`-- --port=4176` 等で変更できる。専用サーバーは許可した共通コード・比較版コード・画像・種族BGMだけを配信し、旧起動・クラウド・保存コードを配信しない。既存のfull／full-offline／demo配布設定から比較版ファイルを除外する。Electronの開発起動は実装済み、比較版の配布パッケージ作成は未実装。
- 初回画面で理解の土台／生活知識／発話形式を独立選択する。既定は全て既知側・短文形式。初期知識の出所は `initial` とし、架空の体験・ノートを生成しない。
- 六段階を `receive` 内で分離し、言語カタログによる読み取りと本人の既知意味・関係の照合を区別する。状態は `knowledge`／`context`／`records`・`notes` に分ける。入力原文・独自の呼び方は翻訳せず保持する。
- 日本語では六種類の声かけの一部文型と短い言い換えを対応カタログに実装。短いお願い・誘い、条件・順序、好み、否定された好み／今の希望、名付け、悲しさの報告と現実の出来事の未知詳細、質問、直前の明確な名付け説明の取り下げを扱う。六言語は休息の誘い・悲しさ・好みの基本入力を先行対応。未対応の文・複文は未理解として残す。
- 条件を理解しても現在の成立は `unknown`。入力理解自体は行動を実行せず、生活側が理解した無条件の休息／散歩の提案に従うかを別に選ぶ。話者の報告と本人の状態、否定と反対評価、出来事の時点と受信時点を区別する。質問理解から回答履歴を捏造しない。しぐさ設定でも理解状態を減らさない。
- 名付けは候補形成／今回の仮採用／関連更新／応用範囲の評価を別処理にする。注目対象が複数なら迷いを保持し、明確な説明による対応だけを根拠として更新する。同じ話者・場面・対象・呼び方の再参照は重複強化しない。同一物の別場面での支持と一般的な関係習得は別。**関係そのものの新規習得と未知生活語の意味獲得は未実装**。共起だけでは候補形成に留め、習得したことにしない。
- 明確な直前の名付け説明を取り下げると、その説明の根拠を履歴付きで失効させる。他の説明・好み等を一括削除しない。文脈・場面に合う既存の呼び方を後続の好みの文の対象として参照できる。
- 初期調整値は直近文脈8件・一度の想起4件・同一物の別場面支持2場面。合意済み定数ではなく調整用の実装値。文脈から外れても選択済み記録は削除しない。
- 内部検証表示は `?debug=1` のみで、通常画面に場面・注目の検証セレクトを置かない。Electronは専用保存、Web確認はセッション内のみとして開始前に区別する。
- 関係の経験習得と、上記の作業語以外の未知語習得、幅広い訂正・対比、発話の成長は未実装。短い返事による会話継続は名付けの範囲を先行対応した。初回比較の最終対象から除外したのではなく、次の実装段階に残す。

### キャラクターと生活の場

以下の仮広場固有の座標・背景・小道は内部検証画面の仕様。標準起動の島描画・場所・移動は上記「既存島での比較起動」が優先し、理解・経験・反応の処理は共有する。

- 歩行中は目的地の左右に合わせてキャラクター画像の向きを変える。認識反応による注目方向より移動方向を優先し、背景・対象の強調・反応記号は反転しない。向きは目的地と現在位置から求め、既存の試作セーブからの再開にも適用する。

- 通常画面は「ことばと、小さな暮らし」。三軸の設定に加え、既存のロボット／精霊／植物の姿を選べる。姿の選択は知識や性格の優劣に結び付けない。`experimental_word_learning_visuals.json` は既存 `data.js` の待機・歩行・横臥フレームから生成し、画像は既存PNGを使う。旧ゲーム状態・個別セーブの姿設定は読み込まない。
- `experimental_word_learning_world.js` が広場・木の実・木陰・小道への移動と注目を所有する。見守り中も、まだ訪れていない／しばらく見ていない場所へ歩き、眺め、木陰で横になる。今回の自律選択は訪問履歴による暫定規則であり、完成した欲求・性格モデルではない。
- 指さしは対象への移動を促す。到着するまではその対象を注目済みにせず、到着後の知覚を学習基盤へ渡す。木の実の個体と採れる場所は区別し、補充された実へ旧個体の呼び名を自動一般化しない。木陰の横臥は既存の睡眠画像を使う。
- 吹き出し、首かしげ、向き、反応記号、現在行動の短い描写で受け取り方を示す。本人が仮に結び付けた名付けは呼び方を疑問形で口にし、しぐさ設定では内容語を発話しない。本人の発話・画面の行動描写・内部診断を区別する。
- 根拠が残る呼び方の単独入力は `reference` として対象を想起できる。移動等で現在注目していなくても、候補が一つなら記憶由来で仮採用する。曖昧なら現在の注目で絞れる範囲に留める。木の実への再訪時にも呼び方を思い出して反応するが、想起や画面表示だけで学習根拠を増やさない。
- 明確に理解した無条件の休息／散歩の提案は、現在の観察への関心と照合する。木の実をまだ眺めていたいときはその希望を伝え、それ以外では対象へ向かう初期規則。提案を選んだ場合のみ入力IDを行動理由に残す。未知・否定・未判断条件を落として実行しない。
- 非表示中、手動一時停止中、入力欄に文字を書いている間は生活・アニメーション時間を止める。復帰時に不在分を進めない。動きを減らす端末設定ではコマ送りや首かしげを抑える。経過時間・移動速度・滞在秒数は調整用の初期値。

### 一画面の操作と会話の継続

- 日本語の状況質問は `core.situationQuestion` で呼びかけ・本人宛ての主題・時点・述語・疑問語尾を組み合わせて解析し、現在／過去の行動、現在の注目、移動先の共通スロットへ接続する。入力原文は保持する。否定、条件、他者主語、未対応の節を削って既知文へ変換しない。現在と過去を混ぜず、未対応は未理解のまま残す。他六言語の入力文型は従来範囲、追加表示文は七言語に対応。
- `world.answerSituation` は現在mode／attention／移動中のdestination、または最後の完了historyだけを参照する。移動・休息・食事・観察・待機を区別し、注目がない間に移動先を見たことにしない。行き先確認には実際の行き先を答え、質問だけで行動を実行しない。道／木陰は既知のwalk／restの範囲で「歩くところ／休むところ」と表現し、新しい名前を学習した扱いにしない。未知語・関係やしぐさ設定の制約を維持し、回答による学習根拠の追加はない。

- 試遊報告から、日本語の朝の挨拶、ひらがなの休息結果質問、木の実があるという報告、今から木陰で休んでほしいというお願いを先行対応。報告だけで未知の場所を見たことにせず、移動の指示とも扱わない。条件・否定や未習得語を落として行動させない。
- 「横になると気持ちいい」は話者の説明として受け取り、本人の感覚へ自動転用しない。「休むことは大事」「体力や眠気が回復するから」は休息の話題を部分的に受け取り、重要性・回復理由の未理解を残す。後者は直前が休息の話題の場合にだけ関連付ける。説明文を短い呼び名へ誤採用しない。
- 「すっぱくない？」では酸味の意味を未習得のまま保ち、否定の答えを捏造しない。質問・否定・食べる意味と実際の甘味記録がある場合は、知らない味の語があることと、実際に甘く感じたことを分けて返す。甘いことを酸っぱくない証明にしない。

- 指さし操作は受付を行動欄へ短く表示し、向かっている目的地のボタンを濃色にする。押下中も色・位置を変える。食事中に移動を受け付けない場合は待つ案内を表示する。
- 肯定／否定の短い返事は汎用の「○○だよ」名付けより優先する。説明直後だけでなく、想起・再訪・名前質問で未確認の呼び名を口にした場合も、その呼び名への確認先を保持する。「そうだよ」を新しい呼び名にしない。肯定後の再参照は確認済みとして発話・ノートへ表示し、同じ確認を独立した新しい語義根拠に数えない。

- プレイ中は画面高に合わせて広場・操作ボタン・ログ・入力欄を収める。横長では広場と会話欄を左右に並べ、900px以下では上下に配置する。長いログだけを内部スクロールし、キャラクターと入力欄を同時に表示する。開始前の説明・設定はプレイ開始後に隠す。Enter送信、Shift+Enter改行、IME確定中のEnterでは送信しない。
- 理解の土台と短文形式がある子は木の実への初回到着で呼び方を尋ねる。答えを必須にせず生活を続ける。日本語では「これはぽぽだよ」「ぽぽだよ」を名付けの候補として受け取り、直前の名前の質問に限り「ぽぽ」だけの短い回答も受け取る。対象が分からない場合は仮の結び付きを確定せず、どれかを尋ねる。
- 新しい名付けに対する本人の確認へ「うん／そうだよ」「ちがう／ううん」等で返せる。対象・話者・直前の質問に結び付け、肯定を新しい独立経験として水増ししない。否定はその説明の根拠だけを失効させ、履歴を保持する。対象から離れた名付け質問や無関係な短い返事を別対象へ勝手に転用しない。
- 「これなに？」には知っている呼び方の範囲で答える。「何してるの？」「何をしてた？」には生活側の現在行動／完了した行動から別々に答える。行動語が未知なら答えを補わない。「どうして休んだの？」で、実際に理解した提案を選んだ場合だけその理由を説明する。提案を聞いただけで行動理由にしない。
- プレイヤーが木の実を好きだと伝えた記録は、後で木の実に近づいた際の話題になる。同じ報告の再言及は一度に抑え、相手の好みを本人の好みとして上書きしない。現在の文型対応は限定的なカタログであり、自由文全般の理解や未知の関係の習得を完成させたものではない。
- 現段階は比較プレイ完成版ではない。生活の調整、未知語・関係の経験習得、ノートでの後日の気づきの追記、友人等による体験比較は残作業として扱う。

### 食事・回復経験と専用保存

- 新しい採取から味覚を生活経験へ接続する。この試作の熟した実は甘く、食べたときに快い味として感じる初期環境設定。個体ごとの恒久的な好みの確定ではない。食事中の感覚と完了経験に味を保持し、空腹軽減から味を推測しない。日本語の「おいしい？」「おいしかった？」「木の実はおいしかった？」は感覚記録と既知語から返答する。食前、味の記録なし、未知語の場合を区別し、旧セーブの経験に味を後付けしない。「休めた？」「疲れはとれた？」も休息の実際の前後差を参照する。
- 質問記録の保存IDは会話入力と同じ input:N 文字列で検証する。質問記録を追加したことを理由に保存停止しない。不正データ・容量不足等での停止方針は維持する。

- 補充方針はユーザーが「近くの木で少量ずつ実り、本人が見つけて採る」を選択。初期2個、上限3個、活動時間65秒ごとに1個が実る初期調整値を採用。果実の観察中に空腹なら採って食べ、5秒の食事完了で空腹が軽くなる。食事中は指さしで食事を破棄しない。食べた個体は berry:N で識別し、次の実の呼び方を前の実から自動転用しない。
- 活動で空腹・疲労が生じ、木陰で11秒の睡眠休息を行う。前後の感覚値と実行時点を本人の経験として保持する。初めは探索し、回復した経験を得た後は空腹・疲労から経験のある場所を選べる。これは非言語的な行動結果の学習であり、未知の語義や文の関係を獲得したことにはしない。疲労時の姿勢・歩行速度、食事の様子、起床を見た目に反映する。数値は比較試遊で調整する。
- 睡眠整理は保持済み報告と本人の経験への参照を notes にまとめる初期実装。原記録を保持し、同じ参照を重複追加しない。取り下げ済み報告は新たに整理しない。ノート表示では原記録の訂正状態を照合する。未知語や本人の自覚していない理由を補わない。
- ユーザー承認により、Electronは専用AppData内の word-life.json に自動保存し、直前版を .backup に保持する。姿・三軸・知識・選択記録・生活状態を保存し、開始画面の「続ける」から再開。不在時間は進めない。会話全文ログは保存しない。既存版のセーブ・クラウドへ接続しない。Webプレビューは保存なし。
- 保存は5秒ごと、会話後、終了前に実施。一時ファイルを置換し、直前版を保護する。暫定上限16 MiB、容量不足・不正形式・読込／書込異常ではその起動中の保存を止めて画面に通知。記録の自動削除や破損原本の自動上書きはしない。バックアップの自動復元、復元選択画面、複数セーブ、既存版との互換移行は未実装。

### 読めるノートと遊びの手がかり

- 「しっかり／ゆっくり／ちゃんと休めた？」の短い言い換えを休息結果の質問として扱う。名前を尋ねた直後の「木の実だよ」は、質問対象と現在注目が一致する場合にその対象の呼び方として受け取る。未知側に木の実の一般的な意味を自動習得させない。

- 右欄の「この子との会話／この子のノート」で切り替える。キャラクターと入力欄は常に表示する。同じ内容の記録を一枚へ集約し、件数と開閉できる履歴を表示する。対象・訂正状態・意味内容の違いは別にする。各分類12項目から表示し、「前の記録も読む」で展開する。集約・表示制限を理由に保存記録を削除しない。新しい記録が増えても開いた履歴は維持する。
- `experimental_word_learning_notebook.js` が保持済みの根拠から表示内容を作る。開く・再読・言語変更で本人の想起や学習を発生させない。既存セーブからも保持済み情報で再生成し、初期知識や根拠のない共起候補を架空のノートへ変えない。
- 「教わったこと」は説明の根拠がある呼び方と、理解済みのプレイヤーの木の実への好みを先行対応。個体への呼び名を種全体へ一般化しない。原説明の取り下げを照合し、取り消し線と取り下げ文を表示。プレイヤーの好みを本人の好みに転用しない。独自の名前は原文のまま表示する。
- 「やってみたこと」は本人の完了した食事・休息の前後差から作る。空腹／疲労の語を知る場合はその内容、未知の場合は体の感覚変化として表す。口頭のしぐさ設定で表示内容を減らさない。食事だけで味覚・好みを生成せず、当時の行動理由や未来の効果を後付けしない。
- 「答えが見つからなかったこと」は質問を理解し、実際に答えが分からないと返した場合だけ `notebookQuestions` へ入力原文を保持する。未理解の発言全てを本人が自覚した疑問として記録しない。後日の回答・気づきによる追記は今後の実装範囲。
- 睡眠で参照整理済みの記録は「眠ったあとに整理」、それ以外は「書き留め」と表示する。ノート文面は出所のある理解・経験を読みやすくしたもので、自由文全般を理解できることを意味しない。
- 会話欄冒頭に指さし・短い声かけ・生活の見守りを案内する。呼び方を受け取った際と十分に理解できなかった際は、プレイヤー向けの補助案内を発話とは異なる表示で添える。案内自体を本人の知識や会話記録へ転用しない。

### 試遊レポート

- 下部の「試遊レポートを保存」から、一つのJSONファイルへ書き出す。Electronは保存先選択、Webプレビューはダウンロード。自動送信しない。開始前説明とボタン説明に収録範囲を表示する。

##### 本人の理解の保持案（2026-09-25・基本構造合意済み）

ユーザーの「本人の理解をどう持つか」の具体化依頼に対する資料。普段の理解と今回の受け取り方を分け、内容ごとに候補・採用状況・確信や迷い・根拠を持つ構造は合意済み。具体的な状態名・候補表現・更新規則は検討中で、実装指示ではない。

- **普段持っている理解**と**今回の発言の受け取り方**を分ける。前者は既存の「知識・育った関連」、後者は「今考えている文脈」に属し、記録に選ばれた場合に当時の受け取り方を「残した記録」へ残す。第四の記憶分類を追加する案ではない。
- 普段持っている理解は、呼び方に結び付く本人なりの意味候補、分かる関係（否定・時点・お願い等）、関連する場面と経験の根拠を持つ。「木陰でじっとする」という本人なりの意味と、仕組みの標準的な休息の意味を区別する。
- 今回の理解は、誰・対象・出来事や状態・肯定否定・時点・条件／順序・発話の働きを、必要な部分だけ関連付けたまとまりとして持つ。原文の未知部分も残せる。本人が読み取れていない条件を、仕組み側の条件ラベルとして本人の理解へ渡さない。
- 各部分に、①本人が受け取った内容の候補、②候補の有無と今回の採用状況、③本人の確信や迷い、④根拠と出所を分けて持つ案。候補の状態は「意味が結び付いていない」「複数候補から決めていない」「今回は一つを採っている」等で表す。直線的な習得段階にはせず、今回採用した解釈でも迷いが残り得る。
- 本人の確信は正解率ではない。標準的な意味とずれていても本人は納得している場合があり、仕組みがずれを検出しただけで本人へ疑問を付与しない。本人が分からなさに気づいているかも別に扱い、未対応箇所があるだけで必ず質問する状態にしない。
- 出所（相手の説明・本人の知覚・推測等）と確信は別にする。「うれしかったと相手が話した」と「うれしかったのだろうという自分の推測」を区別する。条件や否定の必要部分が欠けたお願いを、部分点の合計で理解済みにしない。
- 例: 「食べ終わったら、散歩しよう」で、行動の意味と誘いは分かるが順序が未習得なら、食事・散歩の話題と誘いらしさまで受け取れても、いつ何を求められたかは未解決。仕組みが認識した「食後」を本人の理解へ補わず、「今すぐ散歩」のお願いにも変換しない。本人が別途散歩を選ぶこととは分ける。
- 例: 「今日はピアノの練習がうまくいって、うれしかった」で、話者・今日・成功・気持ちを理解できれば、未知の「ピアノの練習」を残したまま、相手から聞いた出来事として受け取れる。専門知識が未知でも、受け取れた気持ちに応じる材料は持てる。
- 保持構造は採用済み。次の検討点は本人の意味候補の表現、関係ごとの成立に必要な部分、確信・迷い・根拠の更新規則。固定の数値や保存APIはまだ決めない。

1. 今回の受け取り方は直近の文脈へ反映する。長期的な語義・好みの確定、ノートへの採用はそれぞれ別に判断し、全入力の保存や毎回の成長は保証しない。
2. 未知の呼び方は、本人が注目した対象・行動・感覚との仮の関連から始める。理解できる明示的な説明があれば、その説明を根拠に関連付ける。仕組みの正解ラベルでは補正しない。
3. 関係の習得は、声かけと場面・行動・相手の反応が本人の中で結び付いた経験を材料にする。異なる語や場面に共通する働きへ広げるが、回数や必要な経験の種類は今後検討する。
4. 相手が自分の気持ちを言い直し、それを理解できた場合は、今回の相手についての理解を更新する。本人自身の好みや感覚、過去の出来事までは一括上書きしない。
5. 語義の訂正は「以前の説明が取り下げられた」という理解と、本人の関連が変わる過程を分ける。訂正された説明を現在も有効な説明として使い続けることと、昔の経験から連想が残ることを区別する。
6. 過去の見直しは関連記憶を思い出したときに行う。誤った考えの訂正は旧記述を取り消して追記し、未知からの理解は当時の疑問を残して追記する。睡眠中の整理も、本人に残る材料から行う。

#### 反応選択と文型の規則案

- まず根拠のある反応候補を作る。本人が知らない説明、経験していない経験談、相手が述べていない気持ちの断定は候補に入れない。推測する場合は推測として扱う。
- 候補ごとに今回の話題との関係、関心、体調、思い出した経験、直前に伝えた内容を照合する。選択の優先順・重み・揺れは未決定。
- 反復の判定には文面だけでなく「反応の目的・対象・出来事・伝える内容」を使う案。同じ質問の言い換えも反復として扱い得る一方、再質問、新しい出来事、本人の考えの変化、補足が必要な場面では再び話せる。抑制の期間と強さは未決定。
- 文型は、表せる意味・必要な発話能力・省略できない要素を持つ案。否定、誰についての話か、条件等を落とすと別の断言になる候補は使わず、表現可能な部分やしぐさを選ぶ。
- 文型例は「{話題}、{尋ねたいこと}？」「ぼくも、{実際の経験}」「{好みの否定}。{今の希望}」。完成文を抽選する前に、その内容を本人が持ち、今回伝えたいかを判断する。これらは日本語の説明用草案で、製品の固定台詞や全言語共通の語順ではない。
- ノートは同じ内容を口頭能力に縛られず読める文にするが、口頭で言えなかった全内容を自動保存しない。記録内容・履歴と表示文を分け、言語変更で再表示しても本人の記憶更新を起こさない。

#### 一連の例

- 入力「今日はピアノの練習がうまくいって、うれしかった」。仕組みが話者・時点・成功・気持ちを読み取れても、本人が「ピアノ」を知らなければ未知のまとまりを残す。成功とうれしさが分かる子は、相手から聞いた今日の出来事として受け取れる。
- 反応は「よかったね」と受け止める、未知の「ピアノ」を尋ねる、自分の関連する実体験を話す等から選ぶ。ピアノの演奏方法を説明する知識は作らない。どの反応も毎回必須にはしない。
- 記録に残す場合の文案は「『ピアノの練習』がうまくいったと話してくれた。うれしかったそうだ。ピアノって何だろう」。最後の疑問は本人も分からなさを意識している場合だけ付ける。
- 後の「昨日は全然できなかったんだけどね」は、話題継続を受け取れれば昨日の出来事として追加する。今日の成功を取り消さず、対象が曖昧なら仮の対応付けに留める。
- 本人が今は食べたくなく首を振り、相手が「木の実が嫌いなんだね」と返した場合、返事を理解して元の意図との差に気づけば「嫌いじゃない。いま、いらない」等で補足できる。言えなければしぐさ等に留め、相手が話題を変えても解決済み・拒絶と確定せず暮らしを続ける。

| `context.understandings[]` | 今回の入力への受け取り方。話者、誰についてか、対象、内容、否定、時点、条件、発話の働き等の部分と関係 | 入力や関連記憶の想起で作り、追加説明・訂正で該当部分を更新。仕組みの完全な解釈をコピーしない |
| 各部分の `candidateIds / selectedId` | 候補一覧と今回採用する候補。未採用も可能 | 今の話題・注目・理解できる言い回し・経験から選び直す。採用しても他候補や不一致を消さない |
| 各部分の `selectionState` | `unlinked`（意味が結び付かない）、`unresolved`（候補を決めていない）、`selected`（今回採用）の案 | 候補の形成・比較・採用で変わる。習得の固定段階ではなく、selectedでも迷いが残る |
| 各部分の `certainty / awareness` | 今回の解釈への確信・迷いと、本人がその迷いに気づいているか | 本人が受け取れる競合・不一致・新しい裏付けから更新。正解率や長期的な確信とは別。尺度・自覚条件は未定 |
| 各部分の `grounding` | 明示情報／文脈補完／知覚／本人の推測等と参照根拠 | 対象の説明等で根拠を追加・見直し。推測を相手の明示発言へ置換しない |
| `unresolvedLinks[]` | 関係理解に必要だがつながらない箇所 | 本人が必要部分を理解し結べた範囲で解消。未解決でも部分理解は利用可。自動的な自覚・質問は伴わない |
| `context.conflicts[]` | 食い違う内容の参照、対象範囲、保留・部分解消・解消の状態 | 両内容を本人が位置付けられた範囲で更新。今回の候補採用だけでは解消しない |
| 内容ごとの `time` | 聞いた時点、出来事の時点・期間、明示／推測／不明、相対表現の基準 | 理解できた時間情報から更新。後の想起で「昨日」の基準を想起日へずらさない。具体的日付への変換範囲は未定 |
| `context.conditionJudgments[]` | 条件内容、成立と思う／不成立と思う／判断不能、判断時点、根拠・確信 | 本人が受け取れた手がかりの変化時に、条件を参照できれば再判断。内部数値のみで確定しない |
| `context.proposals[]` | 提案内容、条件への参照、今回の誘い／継続的助言／範囲不明、出所 | 説明・取り下げを理解した際に対象の提案を更新。条件成立は実行決定ではない。有効期限は未定 |
| `context.decisions[]` | 選んだ行動、判断時点、実際に使った欲求・想起内容・状況への複数参照 | 行動を選んだ時点で保持する案。結果や後の解釈から当時の動機を後付けしない |
| `context.selfExplanations[]` | 本人が捉えられた理由と根拠。当時の自覚／後の推測・気づきの区別 | 自覚や振り返りから候補化。内部の全判断材料をそのまま本人の考えにしない |
| `context.reactions[]` | 伝えたい内容、未発話／発話済みの区別、実際に表した部分、未表現部分 | 未発話なら追加入力で再選択可。発話済みは当時の内容として扱い、変化は新たな発言へ。未表現の完遂は義務にしない |
| 選ばれた `records.experiences[]` | 本人が気づいた出来事、当時の受け取り方・感覚・評価、元の出来事参照 | 関心・気持ち・理解の変化・今後とのつながりから選択。行動予定だけで結果を記録しない |
| 選ばれた `records.interpretations[]` | 考え、根拠、適用範囲、解釈した時点、以前の版への参照、訂正状態 | 想起を通して理解が変われば追記・訂正。元の経験や当時の自覚を上書きしない |
| ノートの表示内容 | 選ばれた記録・解釈・疑問・訂正履歴から作る表示 | 本人の理解・自覚の範囲を作者の文型で文章化。表示言語変更は説明文の再表示だけで、学習イベントにしない |

| 想起・本人のノート参照・振り返り | 本人が参照できた材料から新しい理解が生じる | 現在の文脈、関連解釈の見直し、追記候補 | 元経験の再加算、当時の自覚の書換え、全記録の再検証 |
| 話題が変わる | 本人が新たな話題として受け取る | 現在の文脈、未発話の反応候補 | 元の内容の全消去・全保存、保留事項の自動解決 |
| 時間が経つ | 時点の区別を保つ。持続の判断は別の根拠・推測に基づく | 現在の状態への判断を必要に応じ見直す | 過去の状態の自動延長、回復等の自動確定 |
| プレイヤーの閲覧・表示言語切替 | 表示処理として扱う | 表示のみ | 本人の想起・知識・確信の更新 |

**更新の共通手順案**

1. 本人が受け取れた新しい材料を、元の入力・出来事へ対応付ける。
2. 関連する対象・相手・場面・時点・意味候補を、本人が参照できた範囲で照合する。対応不明なら保留する。
3. 今回の受け取り方や採用を更新する。行動選択・条件成立・語義の確信をこの段階だけで同時確定しない。
4. 新しい理解や裏付けがあれば、それが支える結び付きだけを長期更新の候補にする。既存根拠の再参照と新経験を区別する。
5. 訂正は対象の現在の扱いを変更し、履歴を残す。派生する考えの再検討は本人が関連を思い出した機会に行う。訂正済みの旧記述を現在の有効根拠として再採用しない。
6. 記録選択と反応選択を別に行い、口頭・ノートには本人が捉えた内容だけを表す。

- 候補採用・新しい裏付け・同じ根拠・迷いの自覚・不一致の部分解消を判定する具体条件。
- 確信の尺度・更新量、注目と想起の選択規則、初期知識と習得状態。

- 保存形式・移行・言語別処理とのAPI。上記の英語名や列挙値を確定したものではない。

#### 関係別の理解成立条件（2026-09-25・設計案）

ユーザーの具体化依頼に対する助手案。既存の合意を必要要素・関係・未解決箇所へ展開したもので、この表の細目や判定方式は未採用。文型の追加や実装開始を承認するものではない。

**共通の判定案**

- 判定の単位は発言全体ではなく、内容同士の一つの関係とする。「質問らしい」と働きを受け取ること、何を尋ねられたかまで結び付くこと、答えを持つことを分ける。
- 関係ごとに、本人がその関係を使えること、必須の役割に本人なりの解釈が入ること、各役割のつながりと否定・条件等の適用先が決まることを確認する。仮に採用した解釈でもつながりは成立し得るが、確信と根拠を保ち、正解・確定とは同一にしない。
- `requiredRoles`（必要な役割）、`unresolvedRoles`（未解決の役割）、`unresolvedLinks`（つながらない関係）、`usedEvidenceIds`（使った根拠）を持つ案。疑問文の「何」「いつ」等の質問先は、回答を求める空欄として分かればよく、答えが入っていないことを未理解とはしない。
- 未知の対象も、今回何について話しているかを指すまとまりとして保持できる。「ピアノの練習」の詳しい意味が未知でも、相手がその出来事をうれしかったと報告した関係は理解し得る。未知対象の性質・用途を必要とする理解は補わない。
- 単語が分かる割合や仕組みの構文解析成功率で理解成立を代用しない。条件・否定・時点・対象等を落として無条件の理解を作らない。未理解の関係につながる部分だけを未解決にし、独立して分かる内容は使える。
- 以下での「必須」はその例の関係を成立させるための要素であり、全発言で全属性を必須にするものではない。明示された重要な限定が未理解なら、その限定を含む全体は未解決として残す。未対応の限定を仕組みも検出できない場合は対応不足として試遊ログで検討し、検出保証をしない。

| 関係・例 | 必要な役割とつながり | 成立時に本人が受け取る内容 | 不足時の扱い／成立から推定しないこと |
|---|---|---|---|
| 状態・出来事の報告「私はまだ食べてない」 | 発言者と内容上の主体、食べる出来事、その主体の経験、否定と「まだ」の時点範囲、報告の働き | 相手は基準時まで食べていないと話している | 主体不明なら誰の状態か未解決。本人への食事のお願いにしない。「まだ」未理解なら全文理解にしない |
| 否定「木の実は嫌いじゃない」 | 好みを持つ人、対象、嫌いという評価、その評価を否定するつながり | その人について、木の実が嫌いという評価を否定している | 好きだとは確定しない。否定先が未定なら否定関係を未解決にする |
| お願い・制止「それは食べないで」 | 働きかける相手、行為者、対象、食べる動作、動作を控える関係、お願いの働き | 該当対象を食べるのを控えてほしいと頼まれた | 対象不明なら制止の働きは分かってもお願い全体は未解決。理解成立は従う決定ではない |
| 誘い「一緒に散歩しよう」 | 誘う相手、参加者、散歩する意味、共同で行う提案の関係 | 相手と一緒に散歩する誘い | 「一緒に」が不明なら単独行動のお願いへ置換しない。参加・経路・開始時刻は自動決定しない |
| 確認質問「木の実は好き？」 | 質問される人、好みの主体、対象、好きという評価、その評価が当てはまるか尋ねる関係 | 自分の木の実への好みを尋ねられている | 好み未形成でも質問の理解は成立し得る。対象不明や評価語未理解は該当部分を未解決にする |
| 内容質問「何を食べたの？」 | 尋ねられる人、行為者、過去の食べる出来事、尋ねたい役割が食べた対象であること | 過去に食べた対象を答えてほしい | 対象は回答欄なので未充足でも質問理解は成立。思い出せない・食べていないことと未理解を分ける |
| 理由質問「どうして休んだの？」 | 尋ねられる人、対象の休息行動、理由を尋ねる関係 | その休息を選んだ理由を尋ねられている | 理由を自覚・説明できなくても質問理解とは別。内部の全判断材料を回答にしない |
| 名付け「これを、ぽぽって呼ぼう」 | 指す対象、原文の呼び方、その対象の呼称として関連付ける関係、説明／提案の出所 | 指されたものの呼び方として「ぽぽ」を受け取る | 呼び方は新語でもよい。対象未特定なら対応は未解決。対象の用途・性質や全員共通の範囲を補わない |
| 時点「昨日は悲しかった。今は元気だよ」 | 感情の主体、各状態、それぞれの時点、各時点を該当状態に結ぶ関係 | 昨日の悲しさと現在の元気を別の報告として受け取る | 正確な暦日への変換は別。昨日だけ分からなければ時点を未解決にし、両状態を同時の事実へ混ぜない |
| 順序「食べ終わったら、散歩しよう」 | 食べる完了という先行出来事、散歩の誘い、各主体、完了後に誘いが適用される関係 | 今回の食事の完了後への散歩の誘い | 完了や前後が不明なら即時の誘いへ変更しない。食事完了の現在判定・想起・実行は別 |
| 条件「疲れたら、休んでね」 | 疲れる状態、その主体、休む提案、条件が成り立つ場合への適用関係 | 疲れた場合に休むことを勧められた | 関係理解は現在の疲労判定と別。条件語の意味不明なら、その条件を含む提案全体は未解決。単発／継続の範囲不明も別に持つ |
| 理由の説明「疲れたから、休んだ」 | 主体、疲れの状態、休んだ出来事、前者を後者の理由として説明する方向と出所 | 相手が疲れを休息の理由として説明している | 時間順序・単なる同時発生と区別。相手の説明から普遍的因果を確定しない |
| 訂正「さっきは間違えた。ぽぽは休むことだよ」 | 説明者、対象の旧説明、新説明の内容、旧説明を取り下げ置き換える関係 | その相手が該当する旧説明を訂正した | 旧説明不明なら新説明を受け取れても訂正先は未解決。新しい意味が未知ならその内容を理解済みにしない |
| 誘いの取り下げ「やっぱり散歩はやめておこう」 | 相手、該当する誘い、誘いを取り下げる関係 | 相手の今回の誘いがなくなった | 誘いの同定不明なら対象を保留。本人の散歩したい気持ちや実行中行動を自動消去・停止しない |

**複合例での確認**

- 「木の実は嫌いじゃないけど、今は食べたくない」は、好みの否定と現在の食欲の否定を別々に持つ。両方を理解できれば併存させ、接続表現だけが不明でも理解できた二つの内容を消さない。対比関係まで理解したとはしない。
- 「木の実を見つけても、赤くなければ食べないで」は、対象、赤いという性質、その否定、条件、食べることの制止の適用先が必要。条件の一部が未理解なら木の実の話題等は使えても、無条件の制止や食べるお願いへ変換しない。複合条件を初回に完全対応する承認ではなく、不足の保持を示す例。
- 「今日はピアノの練習がうまくいって、うれしかった」は、未知の話題のまとまりを保ちつつ、理解できる成功・気持ちの報告へ反応できる。連続して述べられただけで、本人が理解していない因果関係まで確定しない。

**既存の状態案への接続**

1. 言語別の読み取り候補が提示した関係について、本人の `relations` と意味候補を参照する。仕組みの対応と本人の習得を分離する。
2. 各役割へ本人なりの候補を対応付け、明示／文脈補完／推測等の根拠を持つ。
3. 必要な役割・結び付きがそろった関係は今回つながったものとし、不足は `unresolvedRoles / unresolvedLinks` へ残す。これは今回の状態で、関係の恒久習得や語義確信の強化ではない。
4. 質問理解から回答の記憶検索、条件理解から現在の条件判断、お願い理解から行動選択へ進む。それぞれ別の処理で、結果は保証しない。

未決定なのは、表の細目の採否、関係ごとの初期既知範囲、実際の対応文型、曖昧な候補の採用基準、未知部分の切り出し、言語別の語順や省略への対応、複合関係の初回対応範囲。コード変更・実行時検証は行っていない。

#### この草案で残る主な判断

- 話題のつながりに応じた文脈の入れ替えと、外れた内容の記憶への保持を別に判断する方針は合意済み。直近の文脈をどの範囲まで持ち、話題変更・省略・再質問をどう見分けるかは未決定。
- 仮の関連から語義・関係の習得へ進む条件、古い関連の残り方、本人の確信の変化。
- 記憶に残す内容を本人の関心・気持ち・理解の変化・今後とのつながりから選ぶ方針と、今の会話や経験とのつながりから想起し本人の関心・欲求に応じて理解や反応に使う方針は合意済み。具体的な保存・想起の選択規則と、ノート参照・睡眠整理・忘却と容量の関係は未決定。
- 反応候補の優先関係、繰り返しの抑制、行き違いを再び取り上げる条件。
- 発話能力ごとに表せる意味と文型、開始時の三軸（理解の土台・生活知識・発話能力）の具体的範囲。
- 言語別の対応表現、音声入力、保存形式・版管理、比較用ビルドとの接続。詳細APIや数値は本草案では確定しない。

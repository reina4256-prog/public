# TCGリアルタイムP2P対戦仕様

状態: 実装済み・実Firebase／複数PC検証要

## 現在の実装仕様

### 解放と参加

- ディーラー免許皆伝後、カジノのTCGテーブルに `オンライン対戦` を追加する。
- 保存済みの合法な60枚デッキが1つ以上必要。
- シングル戦は人間1～2人、タッグ戦は人間1～4人で開始でき、空席はCPUが担当する。
- 部屋作成と6文字のルームコード参加に、フレンド関係や通常アカウントは要求しない。
- 通常アカウント未ログイン時だけFirebase匿名認証を明示操作後に開始する。匿名ユーザーを既存Firestore機能のログイン済みユーザーとして扱わない。

### 待ち合わせと通信

- Realtime DatabaseのURLは `https://ai-pet-game-default-rtdb.asia-southeast1.firebasedatabase.app`。
- RTDBの `tcg_p2p_rooms/{roomCode}` は参加者の待ち合わせとWebRTCのSDP／ICE Candidate交換だけに使う。カードデッキと対戦盤面はRTDBへ保存しない。
- WebRTC DataChannelは全参加PC間のフルメッシュ。4人時は6本のPC間接続になる。
- 全参加者の接続確認後にRTDBリスナーを解除してルームを削除し、RTDB接続を明示的にオフライン化する。匿名認証で入った端末は匿名セッションも終了し、対戦・再戦中の通信はDataChannelだけで行う。
- ICEは公開STUNのみを使い、TURN中継は持たない。このため厳しいNAT／ファイアウォール同士では接続できない場合がある。
- 大きいデッキ／盤面JSONは約4,000文字ずつに分割し、受信側で復元する。

### ロビーとCPU

- ルーム作成者が最初のホストとなり、参加順に人間を空席へ割り当てる。ホストは開始前に人間同士の席を入れ替え、同じチーム／別チームの組合せを選べる。
- 空席CPUと各人間席の切断時CPUは、常駐ディーラーと現在カジノに来店中の師匠からホストが席ごとに選択できる。同じ師匠の重複指定も許可する。
- 人間は使用デッキを選び、準備完了を送る。全人間の準備と全員間のフルメッシュ接続をホストが確認した場合だけ開始できる。
- CPUは本人の固定60枚デッキを使う。切断後に引き継ぐCPUは進行中の盤面・手札・山札を維持し、以後の判断だけ選択済み師匠のCPU戦術へ切り替える。

### 盤面権威とルール

- ホストだけが正規盤面、カード効果、割り込み、CPU判断、シャッフルその他の乱数を進行する。クライアントは操作意図だけを送る。
- 人間デッキは対戦開始前にDataChannelでホストへ送り、育成後のHP・攻撃力等を含むカード個体JSONをそのまま使用する。
- シングル戦は1対1、共有HP200、各人60枚デッキ。タッグ戦は既存タッグルールを共有し、2対2、チーム共有HP400、各人60枚デッキとする。
- オンラインシングル／タッグは既存 `tcg_tag_core.js` のカード効果、対象選択、人物スキル、守護割り込み、CPU合法手、演出を共有する。
- 通常操作は60秒、守護・人物スキルの割り込みは15秒。時間切れは何もしない扱いとし、通常ターンは終了、割り込みはパスする。
- 対人戦にはカジノコイン報酬を付けない。ローカル保存内にオンラインのシングル／タッグ戦績を別枠で記録する。

### 切断、ホスト移行、再戦

- ホストは操作可能な安定盤面の完全スナップショットを全クライアントへ配布する。
- ホスト以外が切断した場合、その席を事前選択CPUへ切り替えて対戦を続ける。
- ホスト切断時は、残存人間の参加時刻とPeer IDから全端末が同じ新ホストを決定する。最後に受信した安定盤面へ戻し、旧ホスト席をCPU化して続行する。切断直前に解決途中だった演出・操作は安定盤面まで巻き戻る場合がある。
- 全人間との接続が失われた場合は終了する。
- 試合後もDataChannelを維持し、再戦ロビーへ戻ってデッキと準備状態を更新できる。再戦でRTDBへ再接続しない。
- 退出時はDataChannel、PeerConnection、RTDBリスナー、対戦タイマー、分割受信バッファ、古い対戦UIを破棄する。

## Firebase配備要件

- Firebase Authenticationで匿名プロバイダを有効にする必要がある。
- `database.rules.json` をRTDBルールとして配備する。ルールは認証済みユーザーに6文字ルーム配下だけを許可し、それ以外のRTDBパスを拒否する。
- RTDBルールの配備はクライアントコード更新だけでは反映されない。Firebase CLIまたはコンソールで別途反映する。

## 主な状態と実装

- `tcg_p2p_core.js`: 匿名セッション、RTDBシグナリング、フルメッシュ、ロビー、分割送信、タイマー、切断、ホスト選出、再戦。
- `tcg_tag_core.js`: ネットワーク対応の1対1／2対2盤面、権威操作、スナップショット書出し／復元、CPU席への切替。
- `cloud_manager.js`: 通常アカウントと匿名P2Pセッションの分離。
- `database.rules.json`, `firebase.json`: RTDBルール定義と配備設定。

## 確定している将来仕様

- 不特定多数向けランク戦を導入する場合は、ホストによる不正も防ぐ専用バトルサーバー方式を別途検討する。

## 構想段階の案

- TURN中継を導入すれば接続成功率は上げられるが、常時中継の運用費が発生する。
- App Check、ルーム作成頻度制限、期限切れルームのサーバー側清掃を追加する案がある。

## 未決定事項

- STUNのみでの実環境接続成功率が不十分だった場合のTURN提供方法と費用負担は未決定。
- ホスト移行時に解決途中のカード効果まで完全継続するか、現在の安定盤面ロールバックを正式仕様とするかは複数PC試験後に決定する。
